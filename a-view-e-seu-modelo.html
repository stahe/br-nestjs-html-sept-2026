    4. A view e seu modelo

    Até aqui, as ações geravam suas próprias respostas. Em uma aplicação MVC, esse é o papel de uma view: um arquivo que descreve a página HTML, com marcadores para os dados que a ação lhe passa — o modelo da view. Usaremos a engine de views [Handlebars] por meio do pacote [hbs], que a adapta ao [Express].

import { NestExpressApplication } from '@nestjs/platform-express';
import { join } from 'path';

async function bootstrap() {
  // NestExpressApplication: dá acesso aos métodos específicos do Express
  const app = await NestFactory.create<NestExpressApplication>(AppModule);
  // as views ficam na pasta [views], na raiz do projeto;
  // depois de compilado, este arquivo fica em dist/: a raiz é portanto '..'

  console.log('Server started on http://localhost:3000');

    import { Controller, Get, Param, Render, Res } from '@nestjs/common';
import { Response } from 'express';

@Controller()
export class ViewsController {
  // @Render('index'): o objeto retornado pela action é o MODELO da view
  // views/index.hbs; o NestJS chama ele mesmo a engine de views
  @Get()
  @Render('index')
  home(): object {
    return {
      title: 'My first view',
      message: 'This page was built by Handlebars, on the server.',
      time: new Date().toLocaleTimeString('en-US'),
    };
  }

  // res.render(view, model): a view é escolhida DURANTE a execução da action
  @Get('hello/:name')
  hello(@Param('name') name: string, @Res() res: Response): void {
    if (name === 'unknown') {
      res.status(404).render('unknown', { name });
      return;
    }
    res.render('index', {
      title: `Hello ${name}`,
      message: 'This time, the view was chosen by res.render.',
      time: new Date().toLocaleTimeString('en-US'),
    });
  }
}

    • linhas 19–30: quando a view depende da requisição, a ação usa [res.render(view, model)] da resposta do [Express] (injetada por [@Res()]; veja o Exemplo 05). Aqui, o nome [unknown] exibe outra view, com o código de status 404.

    Vamos comentar este código:

    • Linha 9: [{{!-- ... --}}] é um comentário ([Handlebars]): ele não aparece na página gerada (ao contrário de um comentário HTML como [<!-- -->]);
    • linha 10: uma variável ausente do modelo ([nonexistent]) produz uma string vazia, sem erro;
    • linhas 12–13: [{{html}}] escapa os caracteres especiais do HTML ([<] torna-se [&lt;]...): o texto é exibido como está. [{{{html}}}] (três chaves) é inserido sem escape: ele é interpretado como HTML. As três chaves são usadas apenas para HTML gerado pela aplicação, nunca para dados digitados pelo usuário: um usuário poderia injetar HTML, ou até mesmo [JavaScript], na página (um ataque chamado [XSS]);
    • linhas 15–19: [{{#if}}] / [{{else}}] / [{{/if}}]: um bloco condicional. A condição é um valor do modelo, não uma expressão: [false], [undefined], [null], [''], [0] e o array vazio são falsos;
    • linhas 20–22: [{{#unless}}] é o inverso de [{{#if}}];
    • Linhas 26–32: [{{#each}}] repete seu conteúdo para cada elemento de um array. Dentro do bloco, o contexto é o elemento atual: [{{name}}] é o nome do produto atual. Há variáveis especiais disponíveis: [@index] (posição a partir de 0), [@first], [@last]. [../currency] aponta para o contexto pai, [@root.name] para o modelo raiz;
    • linha 36: um [{{else}}] dentro de um [{{#each}}] trata o caso de um array vazio;
    • Linhas 39–41: [{{#with}}] muda o contexto; também é possível usar um caminho relativo (linha 42).

    import { NestFactory } from '@nestjs/core';
import { NestExpressApplication } from '@nestjs/platform-express';
import { NextFunction, Request, Response } from 'express';
import * as hbs from 'hbs';
import { dirname, join } from 'path';
import { AppModule } from './app.module';

const ROOT = join(__dirname, '..');

async function bootstrap() {
  const app = await NestFactory.create<NestExpressApplication>(AppModule);

  // 1. arquivos estáticos: public/css/styles.css é servido como /css/styles.css
  app.useStaticAssets(join(ROOT, 'public'));
  // o Bootstrap é servido diretamente de node_modules, em /bootstrap/
  app.useStaticAssets(join(dirname(require.resolve('bootstrap/package.json')), 'dist'), { prefix: '/bootstrap/' });

  // 2. as views; views/layout.hbs será o layout de TODAS as páginas
  app.setBaseViewsDir(join(ROOT, 'views'));
  app.setViewEngine('hbs');
  // 3. os partials: views/partials/xxx.hbs é inserido por {{> xxx}}
  await new Promise<void>((done) => hbs.registerPartials(join(ROOT, 'views', 'partials'), () => done()));

  // 4. um middleware Express: o que ele coloca em res.locals é
  //    adicionado ao modelo de TODA view
  app.use((req: Request, res: Response, next: NextFunction) => {
    res.locals.path = req.path;
    res.locals.year = new Date().getFullYear();
    next();
  });

  await app.listen(3000);
  console.log('Server started on http://localhost:3000');
}

bootstrap();

    Vamos detalhar este código:

    • linha 14: [useStaticAssets] serve arquivos estáticos de uma pasta: o arquivo [public/css/styles.css] é servido na URL [/css/styles.css] como está, sem passar por um controller;
    • linha 16: o framework CSS [Bootstrap] é servido diretamente da pasta [node_modules], sob o prefixo [/bootstrap/]. [require.resolve] localiza a pasta do pacote [bootstrap], onde quer que ele esteja instalado (aqui em [examples/node_modules]);
    • linha 22: os arquivos da pasta [views/partials] tornam-se views parciais: [partials/navbar.hbs] é inserido em uma view por [{{> navbar}}]. [registerPartials] lê a pasta de forma assíncrona: esperamos que ela termine (a função passada como segundo argumento é chamada no final) antes de iniciar o servidor;
    • Linhas 26–30: um middleware do [Express] , executado antes de cada requisição. O que ele armazena em [res.locals] é adicionado ao modelo de cada view. É assim que fornecemos informações comuns (neste caso, o caminho solicitado e o ano) a todas as páginas sem repeti-las em cada ação.

    import { HelperOptions } from 'handlebars';

// o módulo 'hbs' não tem declarações de tipos: descrevemos o que usamos dele
interface Hbs {
  registerHelper(name: string, fn: (...args: any[]) => unknown): void;
  handlebars: { SafeString: new (html: string) => unknown; escapeExpression(text: string): string };
}

export function registerHelpers(hbs: Hbs): void {
  // {{uppercase name}}: um helper simples, com um argumento
  hbs.registerHelper('uppercase', (text: unknown) => String(text ?? '').toUpperCase());

  // {{#if (eq a b)}}: usado como subexpressão, entre parênteses
  hbs.registerHelper('eq', (a: unknown, b: unknown) => a === b);

  // {{active path '/products'}}: "active" se a página atual estiver sob este caminho
  hbs.registerHelper('active', (path: unknown, prefix: unknown) =>
    typeof path === 'string' && typeof prefix === 'string' && path.startsWith(prefix) ? 'active' : '',
  );

  // {{money amount currency='USD'}}: o ÚLTIMO argumento de um helper é sempre
  // o objeto [options] do Handlebars; options.hash contém os parâmetros
  // nomeados, options.data.root o modelo completo da página (res.locals incluído)
  hbs.registerHelper('money', (amount: unknown, options: HelperOptions) => {
    const currency = options.hash.currency ?? 'EUR';
    const language = options.data?.root?.lang ?? 'en-US';
    return new Intl.NumberFormat(language, { style: 'currency', currency: currency }).format(Number(amount));
  });

  // {{date when}}: uma data no formato do idioma da página
  hbs.registerHelper('date', (when: unknown, options: HelperOptions) => {
    const language = options.data?.root?.lang ?? 'en-US';
    return new Intl.DateTimeFormat(language, { dateStyle: 'full' }).format(new Date(String(when)));
  });

  // {{badge stock}}: um helper que constrói HTML. SafeString diz ao
  // Handlebars para NÃO escapá-lo; cabe então ao helper escapar
  // ele mesmo os dados que insere nele (escapeExpression)
  hbs.registerHelper('badge', (stock: unknown) => {
    const n = Number(stock);
    const cssClass = n > 0 ? 'text-bg-success' : 'text-bg-danger';
    const text = hbs.handlebars.escapeExpression(n > 0 ? `${n} in stock` : 'sold out');
    return new hbs.handlebars.SafeString(`<span class="badge ${cssClass}">${text}</span>`);
  });
}

  @Post()

  @Render('form')
  process(@Body() body: Record<string, string | string[]>): object {
    const input: Input = {
      name: text(body.name),
      password: text(body.password),
      comment: text(body.comment),
      title: text(body.title),
      hobbies: array(body.hobbies),
      country: text(body.country),
      languages: array(body.languages),
      birthDate: text(body.birthDate),
      token: text(body.token),
    };
    return this.model(input, body);
  }

  // o modelo da view: as listas, cada opção sendo marcada
  // checked / selected de acordo com a entrada
  private model(input: Input, received: object | null): object {
    return {
      input,
      titles: this.lists.titles.map((t) => ({ value: t, checked: t === input.title })),

      languages: this.lists.languages.map((l) => ({ value: l, selected: input.languages.includes(l) })),
      received: received ? JSON.stringify(received, null, 2) : null,
    };
  }

export type Errors = Record<string, string>;

export async function validateForm<T extends object>(
  cls: ClassConstructor<T>,
  body: Record<string, unknown>,
): Promise<{ dto: T; errors: Errors }> {
  // 1. objeto recebido -> instância da classe (@Transform / @Type são aplicados)
  const dto = plainToInstance(cls, body);
  // 2. verificação de todas as restrições
  const violations = await validate(dto);
  // 3. mantemos a primeira mensagem de cada campo inválido
  const errors: Errors = {};
  for (const v of violations) {
    errors[v.property] = Object.values(v.constraints ?? {})[0];
  }
  return { dto, errors };
}

    4.7.1. Validação pelo navegador

    Os atributos [required], [maxlength], [min], [max], [type="email"]... instruem o navegador a validar o formulário antes de enviá-lo: o usuário é avisado imediatamente por uma dica de tela (tooltip), sem nenhuma comunicação de ida e volta com o servidor. O estudo de caso, por sua vez, mantém as duas: os atributos HTML5 por conveniência e a validação no servidor por segurança.

    4.8. Exemplo 20: O padrão Post/Redirect/Get

    Quando um formulário POST é enviado com sucesso, a ação pode exibir uma página diretamente. O problema surge se o usuário atualiza essa página (tecla F5): o navegador reenvia o formulário, e a operação é executada uma segunda vez (um pedido feito duas vezes, uma consulta marcada duas vezes...). O padrão Post / Redirect / Get (PRG) evita esse problema: uma ação POST bem-sucedida não gera uma página; em vez disso, ela redireciona para uma página GET. Recarregar essa página envia apenas a requisição GET, que não tem nenhum efeito.

    Resta um detalhe: a página GET precisa exibir uma mensagem (“a tarefa foi adicionada”), embora essa mensagem tenha sido gerada pela ação POST em uma requisição diferente. Ela é transmitida em um cookie de curta duração, que é lido e apagado pela requisição seguinte: trata-se de uma mensagem flash.

    import { NextFunction, Request, Response } from 'express';

const FLASH_COOKIE = 'flash';

// armazena uma mensagem que será exibida pela PRÓXIMA página, e apenas uma vez
export function flash(res: Response, message: string): void {
  res.cookie(FLASH_COOKIE, message, { httpOnly: true, sameSite: 'lax', maxAge: 60_000 });
}

// a cada requisição: a mensagem pendente passa do cookie para res.locals (ou seja,
// para o modelo da view), e o cookie é apagado
export function flashMiddleware(req: Request, res: Response, next: NextFunction): void {
  res.locals.flash = req.cookies?.[FLASH_COOKIE] ?? null;
  if (res.locals.flash) {
    res.clearCookie(FLASH_COOKIE);
  }
  next();
}

// Sem JavaScript, esses formulários são simplesmente enviados sem confirmação.
(() => {
  const modal = document.getElementById('confirmation-modal');
  const message = document.getElementById('confirmation-modal-message');
  let pending = null; // o formulário a enviar se o usuário confirmar

  // 1. interceptamos o envio dos formulários a confirmar
  document.querySelectorAll('form[data-confirmation]').forEach((form) => {
    form.addEventListener('submit', (event) => {
      event.preventDefault(); // o envio é suspenso
      pending = form;
      message.textContent = form.dataset.confirmation;
      modal.classList.remove('d-none'); // a janela aparece
    });
  });

  // 2. os dois botões da janela
  modal.addEventListener('click', (event) => {
    const action = event.target.dataset.action;
    if (action === 'yes') {
      pending.submit(); // envio, SEM disparar novamente o evento 'submit'
    } else if (action === 'no') {
      modal.classList.add('d-none');
      pending = null;
    }
  });
})();
    • Linha 3: o código é envolvido por uma função executada imediatamente, para evitar a criação de variáveis globais;
    • linhas 9–16: o envio de cada formulário que possui o atributo [data-confirmation] é interceptado. [preventDefault()] suspende o envio; o formulário é guardado, a pergunta é colocada na janela ([textContent], e não [innerHTML]: a pergunta é exibida como texto, nunca interpretada como HTML) e a janela é exibida;
    • Linhas 19–27: “Sim” envia o formulário guardado. O método [submit()] de um formulário o envia sem disparar o evento [submit]: não há nova pergunta de confirmação. “Não” oculta a janela.
